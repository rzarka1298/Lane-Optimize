# Results

Current 20-seed evaluation, the four fixes that produced it, a
negative result, and the earlier results they replaced. All numbers
are reproducible: `results/*.csv` contain the raw aggregations and
per-episode rows; plots are generated by `scripts/plot_*.py` from those
CSVs.

## Headline

> With SUMO's lane-change safety check on, **every agent — random,
> two rule-based drivers, DQN-from-scratch, PPO and 4-ego MAPPO — is
> collision-free at every traffic density** over 20 seeds. That turns
> the comparison into the question that matters: who gets through
> traffic fastest. **On high density PPO drives 1 km about 1 s faster
> than the rule-based agents** (paired over the same 20 seeds); at low
> and medium density the field is effectively tied, because most seeds
> finish in identical time behind the same traffic. Getting here meant finding a perception bug that made an
> earlier "0% collisions" result a mirage, a reward that made lane
> changes nearly free, a simulator controller that executed unsafe
> lane changes unchecked, and a reward that couldn't see speed.

| DQN | ≤ 0.28, CI spans 0 | **+0.76 [+0.04, +1.49]** | +1.00 [−0.04, +2.03] |
| `random` | ≤ 0.28, CI spans 0 | **+1.26 [+0.45, +2.08]** | **+1.79 [+0.83, +2.75]** |

On high density PPO is meaningfully faster than the rule-based agents
and `random`; against DQN it's borderline. At low density 13–15 of 20
seeds are exact ties: every agent ends up behind the same traffic and
finishes at the same moment. Lane-change
rate isn't the same as speed: `random` changes lanes most and is
slowest; `safe_rule` barely changes lanes and stays competitive. On
the gauntlet, the escape from the slow lane is easy once unsafe merges
are blocked: every agent averages 30.4–30.6 s and per-seed spreads are
at most ~3.5 s, so it no longer separates agents.

**Why not total return?** Episodes end at the 1 km mark, and the speed
reward is paid per step as `min(v / v_max, 1)`. Summed over an episode
that is about `distance / (v_max · dt)` — the same for every driver
below the limit. Faster driving ends the episode sooner without
earning more, so return doesn't measure driving quality here. Finish
time does.

## The four fixes behind these numbers

### 1. Side-lane observations were mirrored

`laneiq/env/observations.py` read TraCI's `getNeighbors` direction bit
backwards (TraCI: left = 0, right = 1). In the middle lane the
left/right slots were swapped; from an outer lane the one real
adjacent lane was never queried and always read empty. Every agent
and every checkpoint trained before the fix saw this input.

The tests didn't catch it because the unit-test mock had been written
from the same wrong table, so mock and code agreed. A new SUMO test
places cars in known lanes and checks which observation slots they
land in; it fails on the old code.

The fix immediately changed the rule-based `safe_rule` agent, which
needs no training: it went to 0% collisions at every density once it
could see the adjacent lane.

### 2. Lane changes were nearly free → dithering

With correct inputs, every retrained agent started changing lanes back
and forth. `ppo_v5_gauntlet` retrained on fixed observations made 161
lane changes per minute with 40% collisions; MAPPO's median went from 0
to over 100 per minute on medium density. A lane change cost 0.05,
against a speed reward worth up to 1.0 *every step*.

Two changes fixed it:

- **A 1.5 s lane-change cooldown** enforced by the env. While it's
  active the env clears the "lane change available" bits in the
  observation, so the action mask blocks changes automatically and even
  MAPPO, which runs without a mask, can see why a request won't execute.
  The observation shape is unchanged, so earlier checkpoints still load.
- **A 20× lane-change cost** (`w_lane_cost = -1.0`), chosen by a sweep:

| `w_lane_cost` (with cooldown) | Collisions L / M / H | Median lane changes/min, high |
| --- | --- | --- |
| −0.05 (old default) | 0 / 5 / 45% | 18.4 |
| −0.3 | 0 / 15 / 30% | 20.1 |
| **−1.0 → `ppo_v12`** | 5 / 5 / 15% | 5.8 |

These collision numbers are from before fix 3. Training longer (500k
steps) made high density *worse* both with and without the cooldown.

### 3. The simulator executed unsafe lane changes unchecked

Almost every remaining crash was the same event: one lane change, often
within a second or two of spawning, into a car directly alongside the
ego. The observation reported that car correctly. The cause was the
ego's SUMO lane-change mode: mode 0 tells SUMO to execute every
requested change unchecked.

Measured directly in SUMO, with a car parked beside the ego: modes 0
and 1024 execute the change and crash; 256, 512 and 768 refuse it.
(The code had claimed 1024 was "safety-checked"; it's a sublane-model
bit with no effect here.) The env now defaults to **mode 768**: respect
other drivers' gaps, no speed adaptation, so a blocked request is
simply a STAY. It works like a car's lane-change assist: the policy
still decides when and where to change, and SUMO refuses changes that
would cut into another car. The env reports what SUMO actually did
(`info["executed_action"]`), so refused requests don't count as lane
changes or start a cooldown. Mode 0 is still available to reproduce
the earlier dynamics.

### 4. The ego's top speed was a random draw

SUMO samples a speed factor per vehicle unless the vehicle type pins
it. The ego's factor ranged 1.11–1.43 across seeds, so on some seeds it
drove up to 50 m/s on a 36.11 m/s road, and "who's fastest" was partly
luck. The ego's vehicle type now pins `speedFactor="1"`; background
traffic keeps its realistic spread.

## Negative result: rewarding time made PPO slower

To make finishing sooner pay, the per-step alive bonus was turned into
a time penalty (`w_alive = -0.19`, so each second saved is worth +2.0).
The same recipes were retrained under the new environment, one seed
each:

| Model | Finish time (s) | vs current |
| --- | --- | --- |
| `ppo_v13_time_150k`, L / M / H | 29.9 / 31.1 / 33.1 | slower than `ppo_v12` (29.4 / 30.1 / 30.6) |
| `ppo_v14_gauntlet_time_300k` | 32.4 | slower than `ppo_v10` (30.5) |
| `mappo_v4_coop_time_300k`, L / M / H | 26.2 / 26.4 / 26.0 | slightly slower than `mappo_v3` |

All were collision-free, with fewer lane changes. The likely cause is
the safety recipe's per-step penalty for following closer than 1.5 s,
which costs more than the time a pass saves, so passing doesn't pay.
Single training seeds, so some of the gap may be noise. These
checkpoints were **not promoted**. The open follow-up is to rebalance
the unsafe-gap penalty against a time or progress term.

## What changed vs the earlier (Week-7) results

The earlier version of this page claimed the safety-tuned PPO
(`ppo_v2_safety_heavy_150k`) was "the only single-agent policy that
never crashes — 0% collision rate at low, medium, AND high density",
that reward shaping beat training duration, and that `safe_rule` had
15% high-density collisions. Those numbers came from agents that
couldn't see the adjacent lanes (fix 1), under an unchecked
lane-change controller (fix 3), ranked by a return that doesn't reward
speed. In particular, `ppo_v2`'s 0% came from a policy that had
learned never to change lanes. The earlier results are kept below as
history; none of them describe the current system.

The current checkpoints were trained with the same recipes and
step budgets as their pre-fix counterparts (`ppo_v12`: 150k steps;

(kernel-launch overhead dominates), so everything trains on CPU.
